# 面试讲解

模拟问题：请你简单介绍一下这个项目

>**问题分析**
>
>当面试官要求你介绍这个项目的时候，不要简单的就当成对这个项目的描述，而是要当成给了你一次把握整个面试节奏的机会。在介绍项目的时候，需要挖下一些坑让面试官去踩，从而控制住整个面试节奏。
>
>**参考答案**
>
>这是一个 AI 驱动的前端代码生成项目，用户可以直接输入需求描述，或者给一个 Figma 链接，后端会自动选择不同的生成链路，最后产出一个基于 React + TypeScript 技术栈的项目。
>
>这个项目我觉得比较有价值的地方不在前端页面本身，而是在后端这一层，我把原来那种“一次 prompt 直接出代码”的方式，拆成了一个可编排的多阶段工作流。
>
>整个工作流会先做需求分析、能力识别、UI 规划、组件拆分、项目结构设计，再分别生成 types、utils、mockData、service、hooks，之后通过子图并行生成组件和页面代码，最后再做文件组装和 AST 后处理。
>
>这样做的好处是每一步职责比较清晰，出了问题也更容易定位，不会像一个超长 prompt 一样黑盒。
>
>另一个亮点是我在路由层做了输入适配和分流，后端会先判断当前请求到底是普通 prompt、修改类请求，还是 Figma 直连请求，再把它送进不同的图里执行，所以整个系统不是单一链路，而是一个可扩展的多工作流架构。
>
>再一个我比较关注用户体验，所以服务端不是等所有节点跑完再一次性返回，而是基于 LangGraph 的流式执行结果，通过 SSE 把每个节点的中间产物持续推给前端，这样用户能看到分析、规划、生成、组装的全过程。
>
>最后还有一个比较工程化的点，是我没有完全相信大模型的输出，代码组装完成后我又加了一层 AST 后处理，专门去修一些 JSX 对象直接渲染、可选链缺失、空值调用这类比较高频但又很影响运行稳定性的问题，所以这个项目我自己总结下来，重点其实是：
>
>1. AI 工作流编排
>2. 流式交互
>3. 确定性后处理
>
>这三块，而不是单纯调模型生成代码。



模拟问题：你刚才说到了适配器，你能再具体说一下适配器的作用么？

>**问题分析**
>
>这个问题说明面试官已经注意到你前面埋下的“输入适配和分流”这个点了。这里他不是在问你某个具体业务细节，而是在确认你有没有真正理解“适配器”在系统设计里的职责。
>
>回答这个问题时，重点不要跑偏到“我写了几个 if else 判断请求类型”，因为那样会把一个架构点讲成普通业务分支。更好的回答方式是：
>
>1. 先讲清楚适配器解决的核心问题：统一入口、隔离差异、降低主流程复杂度
>2. 再结合你的项目，说清楚它具体适配了哪些输入类型
>3. 最后把话题再引到“可扩展性”和“后续新增链路成本低”上，让面试官继续追问架构设计
>
>**参考答案**
>
>我这里说的适配器，本质上是放在工作流执行之前的一层“输入标准化和路由分发”机制。
>
>因为这个项目的入口虽然统一是聊天接口，但是用户实际发过来的请求类型并不一样。
>
>- 有的是普通 prompt，想直接根据需求生成项目；
>- 有的是 Figma 链接，希望走设计稿直连链路；
>- 还有的是修改类请求，可能是基于已有上下文继续调整代码。
>
>如果这些差异都直接堆到主流程里处理，主图会变得很乱，后面再加新类型也会越来越难维护。
>
>所以我单独做了一层适配器。它主要有三个作用：
>
>1. 先识别当前请求属于哪一类输入
>2. 把不同格式的输入转换成对应工作流能直接消费的统一结构
>3. 再决定应该进入 Traditional 图还是 Figma 图这类具体执行链路
>
>这样做以后，聊天路由本身就比较薄，它只负责收请求、调用适配器、拿到结果后启动对应的 Agent，而不用关心每种请求到底怎么判断、怎么组装输入。
>
>对这个项目来说，我觉得适配器最大的价值有两个：
>
>- 第一，是把“入口复杂度”和“工作流复杂度”拆开了。
>
>入口层只做分流，图内部只关注执行步骤，这样职责比较清晰。
>
>- 第二，是可扩展性会更好。
>
>比如以后我要新增一种请求类型，不管是图片生成、局部重构，还是别的多模态输入，我理论上只需要新增一个适配器，定义它的识别规则和输入转换逻辑，再挂到注册表里，而不用去大改原来的主流程。
>
>所以我在这个项目里理解的适配器，不是一个简单的工具函数，而是一层很关键的架构边界。它把“外部输入的不确定性”和“内部工作流的稳定性”隔离开了。这样系统就更容易扩展，也更容易维护。



模拟问题：说一下AST处理这一块儿，具体是做了什么事情？整个AST后处理你是怎么设计的？

>**问题分析**
>
>这个问题说明面试官已经顺着你前面埋的“确定性后处理”这个点追下来了。这里他其实想确认两件事：
>
>1. 你到底是不是只会说“我做了 AST”，还是你真的知道它在项目里解决了什么问题
>2. 你有没有把 AST 当成一个稳定性的工程方案来设计，而不是随便写几个字符串替换脚本
>
>所以回答的时候，要避免两种问题：
>
>1. 不要把 AST 讲成编译原理大课，面试官通常不是来听你背 Babel 原理的
>2. 不要只说“我修了一些 bug”，这样显得太浅，体现不出你的设计思路
>
>更好的讲法是：
>
>1. 先说为什么要加 AST 后处理
>2. 再说它放在整个生成链路里的哪个位置
>3. AST后处理的设计是如何设计的
>4. 然后讲它主要修哪些高频问题
>5. 最后强调为什么用 AST，而不是正则或字符串替换
>
>这样一来，面试官后面就很容易继续问你：
>“你为什么把它放在最后一层？”
>“你具体怎么识别 JSX 里的问题？”
>“AST 和 prompt 优化之间你是怎么分工的？”
>
>**参考答案**
>
>好的，老师。我这边做 AST 后处理，核心原因其实很简单，就是我没有完全相信大模型生成出来的代码一定能稳定运行。
>
>因为这个项目最后要产出的是一个可以直接在 Sandpack 里跑起来的 React + TypeScript 项目，所以我不希望流程停留在“模型看起来写得像对了”这个层面，而是希望在落地成文件之后，再做一层确定性的静态修复。
>
>所以我把 AST 后处理放在了整个生成链路的最后面。也就是先让前面的节点完成分析、规划、代码生成和文件组装，等最终的文件集合已经形成之后，再统一对这些文件做一次 AST 分析和修复。这样做有一个好处，就是它面对的是最终产物，而不是中间片段，所以修复范围是完整的，比较适合做兜底。
>
>具体做的事情，主要是修一些大模型生成 React 代码时很常见、而且一旦出现就会直接影响运行稳定性的问题。比如：
>
>1. JSX 里把对象类型字段直接渲染出来，运行时会报 Objects are not valid as React child
>2. 某些链式访问少了可选链，数据一旦为空就会触发 Cannot read properties of null 之类的问题
>3. 一些数组方法、字符串方法或者属性访问没有做空值保护，代码看起来没问题，但运行时其实很脆弱
>
>这些问题有个共同特点，就是它们不是业务逻辑错误，而是“生成代码在运行稳定性上不够严谨”。这种问题如果完全靠 prompt 约束，效果不一定稳定，因为模型有时候会遵守，有时候不会，所以我更倾向于在最后加一个确定性的修复层。
>
>从设计上来说，我当时是按“分析”和“修复”两层来做的。
>
>- 第一层是 AST 分析。
> 我会先把组装后的 Sandpack 文件集合拿出来，解析成 AST，去识别哪些表达式出现在 JSX 里、哪些访问链有潜在空值风险、哪些调用在类型上或者语义上存在明显问题。
>
>- 第二层是规则化修复。
> 也就是说我不是让模型二次改代码，而是基于 AST 节点做程序化变换，把有问题的表达式替换成更安全的写法。这样修复结果是可预期的，而且不会把别的代码一起误伤。
>
>我这里为什么坚持用 AST，而不是直接用正则或者字符串替换，主要有两个原因：
>
>1. AST 能理解代码结构，知道一个表达式到底是在 JSX 里渲染，还是只是在普通函数里定义变量
>2. 它可以做比较精确的局部修改，不容易把相似文本误替换掉
>
>所以这块我自己会把它定义成一个“运行前的稳定性兜底层”。
>
>前面的 LLM 负责生成，AST 后处理负责把高频、可识别、可修复的问题收口。这样整个系统就不是完全依赖模型质量，而是把 AI 生成和确定性工程手段结合起来了。



模拟问题：你说整个项目是通过大模型来生成的，那么如何降低大模型的幻觉？或者换句话说，如何提高大模型生成代码的质量？

>**问题分析**
>
>这个问题其实是大模型项目里非常核心的一个追问。面试官想确认的，不是你会不会调 API，而是你有没有把“大模型不稳定”这件事当成一个工程问题来处理。
>
>这里回答时，最好不要只说“我把 prompt 写得更细了”，因为那样会显得你对模型质量的控制手段比较单一。更好的回答方式是把它拆成一个完整的质量控制链路去讲，让面试官感觉到：你不是迷信模型，而是在用一整套工程手段约束模型输出。
>
>这类问题通常可以按下面这个思路回答：
>
>1. 先承认大模型天然有幻觉和不稳定性
>2. 再讲你在生成前、生成中、生成后分别做了哪些约束
>3. 最后强调你的核心思路不是“让模型自由发挥”，而是“尽量缩小模型的自由度”
>
>这样面试官后面就很容易继续问：
>
>- “Schema 你是怎么设计的？”
>- “公共提示词具体约束了什么？”
>- “retry 是怎么做的？所有失败都重试吗？”
>
>回答的时候，分为好几个层面去回答，每一个层面都按照下面2个点：
>
>1. 这个层面的处理是怎么做的
>2. 这个层面的处理意义是什么
>
>**参考答案**
>
>降低大模型幻觉，核心不是单点优化 prompt，而是尽量把模型的输出空间收窄，让它在一个比较受控的范围内生成。所以在这个项目里，我主要是从三个层面去提高代码质量的：
>
>1. Schema 约束
>2. 提示词分层约束
>3. 以及失败重试和后置校验
>
>先说 Schema 约束。
>
>这个项目不是让模型直接返回一大段自由文本，而是让不同节点尽量返回结构化结果。比如分析节点、能力识别节点、组件拆分节点，本质上都更适合输出 JSON 结构，而不是一段自然语言描述。这样做的好处是，模型一旦偏题、漏字段、字段类型不对，我们就能比较早地发现，而不是等到最后组装代码的时候才发现整个链路已经歪了。
>
>我理解 Schema 约束最大的价值是两点：
>
>1. 它能把“结果好不好”先变成“格式对不对”
>2. 它能让后续节点消费上游结果时更稳定，因为字段是约定好的，不需要再去猜模型到底想表达什么
>
>第二块是提示词分层。
>
>我没有把所有要求都塞进一个超长 prompt，而是把公共约束和节点级约束拆开。公共提示词主要负责那些所有代码生成节点都应该遵守的规则，比如技术栈、代码风格、输出边界、不要随意编造依赖、尽量和已有上下文保持一致；而节点自己的提示词，再补充当前阶段的具体目标和输入上下文。这样做的好处是，一方面公共规则可以复用，另一方面每个节点只关心自己这一小段任务，模型不容易因为上下文太杂而跑偏。
>
>从经验上说，想降低幻觉，一个很重要的原则就是不要给模型一个过大的开放题。
>
>比如如果我要生成整个项目，直接让模型“一次性输出完整代码”，它很容易凭空补细节、自己发明文件结构，或者前后不一致；但如果我把它拆成分析、结构、类型、服务、页面、组件这些小步骤，每一步只做一件事，模型的稳定性会明显好很多。
>
>第三块是 retry。
>
>因为大模型的输出有波动，所以有些失败不能简单看成“功能没写对”，而是要区分到底是格式失败、解析失败，还是内容质量明显不达标。对这种情况，我会做有条件的重试。比如结构化输出解析失败、关键字段缺失、结果为空、或者生成内容明显不符合约束时，可以触发 retry；但不是所有异常都无脑重试，因为如果是输入本身有问题，重试是没有意义的。
>
>我对 retry 的理解不是“多试几次碰碰运气”，而是把它当成一个质量兜底机制。
>因为模型第一次失败，很多时候不是逻辑完全不会，而是输出格式偏了、某个字段漏了、或者当次采样不稳定，这种场景下有限次 retry 是有价值的。
>
>除了这三块，我还做了两层补充措施。
>
>第一层是流程拆分。
>
>也就是我前面提到的，把一个大任务拆成多个节点，让每一层都只解决一个明确问题。这个本身其实也是在降低幻觉，因为任务越聚焦，模型越不容易胡乱发挥。
>
>第二层是后置确定性校验。
>
>就算前面已经做了 Schema 和 prompt 约束，我还是不会完全相信模型，所以在最后代码组装完成后，又加了一层 AST 后处理，去修一些高频运行时问题。也就是说，我并不是把“提高代码质量”完全押在模型身上，而是把模型约束和程序化修复结合起来。
>
>所以如果总结一下，我在这个项目里降低幻觉、提高代码质量的核心思路其实是四步：
>
>1. 用 Schema 把输出结构固定住
>2. 用公共提示词和节点提示词把生成边界收窄
>3. 用工作流拆分降低单次任务复杂度
>4. 用 retry 和后置校验做质量兜底
>
>本质上，我做的是“让系统对模型更有约束力”。这样代码生成的稳定性会比单纯堆 prompt 好很多。
